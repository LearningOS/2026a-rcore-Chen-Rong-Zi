# lab5实验报告
## 功能实现
本次实验实现了死锁检测功能。为进程控制块增加死锁检测开关，并新增系统调用sys_enable_deadlock_detect用于按需开启/关闭检测（参数合法校验，非法返回-1）。在任务控制块内为每个线程维护互斥锁与信号量的资源持有记录，同步原语侧补充查询接口（互斥锁是否被锁、等待队列中的线程），信号量记录初始计数。sys_mutex_lock与sys_semaphore_down在确实要阻塞之前先做银行家算法安全性检查：从各线程持有记录得到Allocation，从等待队列得到Need，从锁状态和信号量计数得到Available，将请求者需求加1后跑安全性算法，若系统不安全则拒绝请求并返回-0xdead，不进入阻塞；安全则正常获取资源并更新持有记录。sys_mutex_unlock与sys_semaphore_up在释放后扣减持有记录。条件变量按手册说明不参与检测混用。此外补全了框架未实现的sys_get_time，将时间写回用户传入的结构体。

## 问答作业

### 1. 主线程退出时需要回收的资源有哪些？其他线程的 TaskControlBlock 可能在哪些位置被引用，分别是否需要回收？

主线程（0号线程）退出即整个进程退出，此时要结束该进程管理的所有线程并回收资源：

- 需要回收的资源：各线程的用户态资源，即 TaskUserRes 中分配的 tid、trap context 物理页、用户栈物理页；各线程的内核栈 KernelStack；以及进程本身的地址空间（memory_set）等。

- TCB 可能被引用的位置：
  1. `process/tasks` 向量：每个 ProcessControlBlock 保存着所有线程的 Arc<TaskControlBlock>。这是最直接的引用，进程退出时需要清理（如置 None 并随之释放对应资源），否则线程资源无法回收。
  2. 各同步原语（mutex/semaphore/condvar）的 wait_queue 中：尚在等待的线程会把自己的 TCB 引用挂进等待队列。这些引用同样需要清理——如果队列里的 Arc 不清掉，内核栈等资源就释放不掉。有个细节：线程在等到退出时，其 TaskUserRes 可能已经先被置成 None，所以遍历队列做清理时要容错，引用已失效（res 为 None）的就跳过资源释放，只把引用本身清掉。
  3. pid2process 等全局映射：thread id 到 TCB 的映射中如果还挂着对应表项，也需要删掉。

### 2. 对比 Mutex1 与 Mutex2 两种实现，二者有什么区别？这些区别可能会导致什么问题？

两种实现的区别在于对"锁的状态"和"等待队列"关系的处理：

- Mutex1：lock 时发现锁已被占用，先把自己加入等待队列，再阻塞，被唤醒返回后**回到循环重新检查** locked 是否可以拿锁；unlock 时把 locked 置 false，然后唤醒队首任务。
- Mutex2：把"唤醒"当作锁所有权的直接转移。unlock 时如果等待队列非空，就不动 locked 标志，直接唤醒队首，对方醒来即视为已持锁；只有队列空了才把 locked 置 false。lock 也没有循环重试。

可能导致的问题：

- Mutex1 存在"入队之后、真正阻塞之前"的窗口。在这段间隙里，如果发生中断抢占或其他任务执行了 unlock，把本任务从队列里拿出来唤醒（状态改为可运行），而它随后才执行 block，那么这次唤醒就丢失了——它 block 之后没人再来唤醒，会永远卡死。另外它反复重查、重入队列的逻辑也更绕，容易出状态不一致的问题。
- Mutex2 靠"唤醒即交付锁"这一约定做隐式状态转移，加锁、唤醒、置位的时序更原子，出错点少；但它要求 unlock 时严格遵守"队列里有人就绝不碰 locked 标志"的约定，一旦破坏这个约定（比如队列有人时又把 locked 置 false），锁就会被"凭空"多出一份，出现两方同时持锁的情况。
